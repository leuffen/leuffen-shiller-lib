# AI Usage Info – Shiller

Shiller richtet eine Website aus den Vorlagen eines Theme-Pakets ein und passt
installierte Markdown- und YAML-Dateien an einen Projektkontext an.
Die [README.md](README.md) zeigt die CLI-Befehle in Ausführungsreihenfolge.
Für die Vorbereitung eines ThemeJS2-Pakets gilt der
[Shiller Theme Setup Skill](skills/shiller-theme-setup/SKILL.md).

Die [kommentierte .shiller.yml](docs/.shiller.yml) dokumentiert alle
unterstützten Projektfelder, Defaults und Pfadbezüge. Bei neuen Projekten
als Vorlage verwenden; optionale lokale Pfade nur bei vorhandenen Dateien
aktivieren. `version: 1.0` und `adapter: jekyll-polyglot:1.0` (oder `jekyll-legacy:1.0`)
sind Pflichtfelder; unbekannte oder fehlende Angaben lösen eine
`ConfigurationException` aus.

Für ausgecheckte ThemeJS1-Projekte ohne `.shiller.yml` vor dem
Repository-Zugriff `(new \Leuffen\Shiller\LegacyUpdate\LegacyUpdater())->update($projectRoot)`
aufrufen. Der Updater legt die Legacy-Konfiguration sowie `.shiller.d/static-context.md`
und `.shiller.d/user-rules.md` an; vorhandene Dateien bleiben unverändert. Siehe
[Legacy-Checkout](README.md#legacy-checkout-initialisieren).

## Verzeichnisstruktur

Das Theme-Paket liegt im Website-Projekt unter
`node_modules/@leuffen/themejs2/` und stellt `_tpl/` und
`skills/` bereit. `_tpl/_root/` wird bei `init` kopiert;
andere Vorlagen werden über Tags ausgewählt. Skills bleiben im Paket.

```text
website/
|-- .shiller.yml
|-- .shiller-context.d/
|   |-- project.md
|   `-- raw/
|-- docs/
|   |-- index.md
|   `-- _data/general.yml
`-- node_modules/
    `-- @leuffen/themejs2/
        |-- _tpl/
        |   |-- _root/
        |   |   |-- .shiller.yml
        |   |   |-- .shiller-context.d/project.md
        |   |   `-- docs/_data/general.yml
        |   |-- pages/index.base.md
        `-- skills/edit-website/SKILL.md
```

`_tpl/_root/docs/` wird zu `website/docs/`, andere
`_tpl/_root/`-Dateien in die Projektwurzel kopiert. `docs/`
ist der Standard-Document-Root. Die Startdatei
`.shiller-context.d/project.md` enthält die Website-Fakten. `context_files`
in `.shiller.yml` wählt den allgemeinen AI-Kontext als String oder Liste.
Ohne Angabe wird nur die vorhandene `project.md` geladen; keine automatische
Verzeichnissuche. `[]` deaktiviert den Projektkontext. `context build` bleibt
unverändert.

## Beispiel für ein Theme-Template

`_tpl/pages/index.base.md`:

```markdown
---
shiller:
  tags: [base]
  target: index.md
layout: website
title: Startseite
---
# Willkommen
```

Die Datei wird bei `--tags base` als `docs/index.md`
installiert. `shiller.tags` steuert die Auswahl,
`shiller.target` den Dateipfad relativ zum Document Root ; die installierte Markdown-Datei speichert stattdessen nur
`shiller.source: pages/index.base.md` als Herkunftspfad unter `_tpl/`.
Für andere Textdateien dient das Suffix `.template`;
dabei werden der YAML-Header und das Suffix nicht ins Ziel übernommen.

Die kopierte `.shiller.yml` im Projekt-Root enthält:

```yaml
version: 1.0
adapter: jekyll-polyglot:1.0
template_dir: node_modules/@leuffen/themejs2/_tpl
skills_dir: node_modules/@leuffen/themejs2/skills
context_files: .shiller-context.d/project.md
```

## CLI: Projekt erstellen und Inhalte bearbeiten

Befehle in der Website-Projektwurzel ausführen; das PHP-Paket
`leuffen/shiller-lib` und das ThemeJS2-npm-Paket müssen vorhanden sein.

```sh
# Einmalig: Startstruktur und die Variante "base" installieren.
./vendor/bin/shiller init --template-dir ./node_modules/@leuffen/themejs2/_tpl --tags base

# Optional: weitere Variante gezielt installieren.
./vendor/bin/shiller install --tags "theme:osman"

# Nur wenn neue Rohdaten unter .shiller-context.d/raw/ liegen:
./vendor/bin/shiller context build

# Eine installierte Datei an Projektkontext und Theme-Skills anpassen.
./vendor/bin/shiller adapt --select index.md

# Alternativen: mehrere Dateien oder Original wiederherstellen.
./vendor/bin/shiller adapt --select "index.md,_data/general.yml"
./vendor/bin/shiller revert index.md
```

## AI Editor

`Leuffen\Shiller\Automation\ShillerAiEditorAction` erzeugt mit
`inlineCompletion(InlineCompletionRequest)` und `inlineEdit(InlineEditRequest)`
Vorschläge, ohne Dateien zu ändern. Die DTOs liegen unter `Automation\DTO`.
Ohne `previousResponseId` wird der Ausgangskontext erstellt; danach immer
`responseId` aus der Antwort erneut als `previousResponseId` verwenden.
Die aufrufende Anwendung muss die ID gegen fremde Kontexte absichern.
Die Action baut ihr Environment mit `AiContext` auf. Optional kann ein
noch nicht gestarteter, konfigurierter `AiContext` als `environment` übergeben
werden. Inline Completion verwendet `gpt-6-luna` mit Reasoning `none`,
Inline Edit `gpt-6.2-sol` mit Reasoning `low`. Die Modelle lassen sich über
die Constructor-Argumente `completionModel` und `model` (Edit) überschreiben;
die Modellwahl gilt auch für ein injiziertes Environment.
Inline Edit erlaubt eine leere `selection` mit `from === to` für Einfügungen
am Cursor. Das Output-Limit beträgt 4096 Tokens plus eine Schätzung des
Tokenumfangs der Auswahl (drei UTF-8-Bytes pro Token).
`usage` und `initializationUsage` enthalten die Usage der jeweils
letzten Provider-Response; der aktuelle Editor-Ablauf nutzt keine Tools.
Siehe [21 – AI Editor](examples/21-ai-editor.php).

## AI-Projektkontext

```php
$site = new \Leuffen\Shiller\Access\ShillerRepository('/srv/site/docs', projectRoot: '/srv/site');
$context = new \Phore\AiHarness\AiContext();
$site->configureAiHarness($context);
```

Die Methode registriert Projektkontext, Skills, Systemanweisungen,
Templates und User Rules anhand von .shiller.yml. Der Aufrufer bindet
das Website-Dateisystem mit eigener Policy und den zusätzlichen
Schreibsperren aus `$site->getAiResourceWriteIgnore()` ein.
`allowUserRulesEdit: true` gibt nur die konfigurierte Regeldatei frei;
dauerhafte Regeln werden nur nach ausdrücklichem Speicherauftrag geändert.
`$site->getPageIndexCsv()` liefert den mehrsprachigen Seitenindex.
Siehe [AI-Projektkontext](docs/ai-context.md).
